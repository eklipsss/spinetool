# Алгоритм предобработки шипиков

## 1. Цель разработки

Необходимо разработать воспроизводимый и отказоустойчивый пайплайн предобработки полигональных сеток дендритных шипиков для последующего обучения генеративной модели геометрии шипиков.

Исходные данные имеют структуру:

```text
<dataset>/
  <neuron_id>/
    summary.json
    soma/
      soma_mesh.off
    limb_<limb_id>/
      limb_mesh.off
      limb_skeleton.npy
      branch_<branch_id>/
        branch_mesh.off
        branch_skeleton.npy
        spines/
          spine_<spine_id>.off
```

Особенности исходных данных:

1. часть объектов, сегментированных как `spine`, может фактически являться фрагментом ствола дендрита;
2. один биологически непрерывный branch без ветвления может быть ошибочно разбит на несколько последовательных branch;
3. `spine_<id>.off` является незамкнутой полигональной поверхностью: в области крепления к дендриту присутствует основной открытый контур, дополнительно могут присутствовать мелкие побочные отверстия;
4. mesh имеют разное число вершин и граней;
5. реальные размеры нельзя индивидуально нормировать до unit cube, поскольку размер является биологически значимым признаком.

**Пайплайн предобработки состоит из нескольких независимо запускаемых этапов:**

1. запаивание mesh шипиков с отдельной фиксацией области крепления к дендриту;
2. обнаружение ложных шипиков;
3. перевод исходного и запаянного mesh шипика в единую локальную систему координат;
4. логическое объединение ошибочно разделённых branch и обновление метаинформации шипиков;
5. проверка геометрической корректности `sealed_local` mesh;
6. преобразование `sealed_local` mesh в облака точек фиксированного размера;
7. подготовка SDF-выборок для обучения неявного декодера поверхности;
8. вычисление морфологических метрик дендритныхх шипиков;
9. формирование метаинформации дендритныхх шипиков.

Этапы 6–9 (и, по умолчанию, `train_eligible` в manifest) выполняются для шипиков со статусом `valid` **и** `needs_review` (`allow_needs_review: true` по умолчанию, см. §3.5.4 и §5) — сам факт `needs_review` не является геометрическим браком, это пометка для ручного разбора. Объекты `invalid` сохраняются в журнале и в структуре `/preprocessed/`, но обучающие представления для них не формируются. Строгий режим (только `valid`) включается `allow_needs_review: false`.


## 2. Общие требования
### 2.1. Независимый запуск этапов

Необходимо предусмотреть возможность:

- запуска любого этапа отдельно;
- запуска полного pipeline;
- повторного запуска только объектов, завершившихся ошибкой;
- принудительного пересчёта выбранного этапа;
- обработки только выбранного датасета / нейрона / limb / branch / spine;
- тестового запуска на ограниченном числе объектов.

### 2.2. Исходные файлы не изменять

Исходные `.off` и `.npy` запрещено перезаписывать.

Все результаты сохраняются в отдельную директорию `/preprocessed/` с зеркальным сохранением иерархии исходного датасета. Папка `/preprocessed/` создаётся внутри корня конкретного датасета, структура имеет вид:

```text
<dataset_name>
  preprocessed/
    <neuron_id>/
      limb_<limb_id>/
        branch_<branch_id>/
          spines/
            spine_<spine_id>/
              ...
```

Например, для исходного `spine_123.off` из датасета Minnie результат должен однозначно находиться внутри:

```text
/Minnie/preprocessed/<neuron_id>/limb_<limb_id>/branch_<branch_id>/spines/spine_123/
```

Для любого результата должны однозначно восстанавливаться:

- dataset;
- neuron_id;
- limb_id;
- original_branch_id;
- spine_id;
- исходный путь.

### 2.3. Батчи, checkpoint и resume

Все этапы должны поддерживать фиксированный `batch_size`, задаваемый пользователем.

После обработки каждого batch результаты немедленно сохраняются на диск. Ошибка следующего batch не должна требовать пересчёта предыдущих.

Для каждого объекта и этапа хранить состояния:

```text
pending
processing
success
failed
skipped
needs_review
```

Использовать `processing_state.sqlite` как основной журнал и экспортировать итоговые таблицы в `parquet`.

Минимально сохранять:

- dataset;
- neuron_id;
- limb_id;
- branch_id;
- spine_id;
- stage;
- status;
- время начала/окончания;
- длительность;
- текст ошибки;
- входной/выходной путь;
- версию алгоритма;
- hash конфигурации.

При `--resume` объекты со статусом `success` и той же конфигурацией пропускаются.

#### Атомарное сохранение

Результат сначала писать во временный файл:

```text
spine_123.sealed.off.tmp
```

и только после QC переименовывать в финальный.

### 2.4. Progress bar

Для каждого этапа реализовать два уровня прогресса.

**Общий прогресс**, пример:

```text
Dataset Minnie
Spines processed: 18 420 / 73 512
Batches: 184 / 736
Success: 18 217
Failed: 31
Needs review: 172
```

**Прогресс текущего объекта**, пример:

```text
spine_123
[1/6] load mesh - <время выполнения>
[2/6] detect boundary loops - <время выполнения>
[3/6] build skeleton - <время выполнения>
[4/6] project to dendrite skeleton - <время выполнения>
[5/6] compute QC features - <время выполнения>
[6/6] classify - <время выполнения>
```

Рекомендуется `rich` или вложенный `tqdm`.

## 3. Описание этапов

### 3.1. Этап 1. Запаивание мэшей шипиков

Алгоритм уже реализован и опробан в ноутбуке `notebooks/exploratory/test_skeleton.ipynb`, использовать данную реализацию.

#### 3.1.1. Определение области крепления до запаивания

Перед заполнением отверстий необходимо отдельно определить, какой boundary loop соответствует **реальной области крепления шипика к дендриту**. Эта информация должна сохраняться отдельно от информации о мелких побочных отверстиях.

Алгоритм поиска области крепления:

1. В исходном незапаянном mesh найти все `boundary edges` — рёбра, принадлежащие ровно одной грани.
2. Собрать boundary edges в замкнутые циклы `boundary loops`.
3. Для каждого цикла вычислить:
   - периметр;
   - площадь отверстия;
   - центр цикла;
   - минимальное расстояние от центра цикла до `branch_skeleton.npy`.
4. Выбрать `attachment loop` по следующим критериям (веса в `sealing.attachment_weight_{perimeter,area,distance}`, `spine_preprocessing.yaml`):
   - большой периметр (вес `0.32`);
   - большая площадь (вес `0.28`);
   - малое расстояние до скелета родительского branch (вес `0.4`, **наиболее весомый критерий** — решение по итогам ручной проверки реальных шипиков, см. `CLAUDE.md` "Модели генерации шипиков" / история правок весов: расстояние до скелета оказалось надёжнее периметра/площади — конкурирующая дырка с большим периметром/площадью, но далеко от скелета, почти всегда ложная (часть branch) или дефект сегментации (голова шипика отрезана), тогда как настоящая область крепления физически ближе к скелету дендрита, чем любая другая часть шипика).
5. Если критерии дают неоднозначный результат, объект помечается `attachment_ambiguous=true` и `needs_review`, автоматически выбирать один из близких кандидатов запрещено.

**Fallback после запаивания (реализовано в `select_attachment_patch`, `spine_geometry.py`).** Шаг 2 (сборка `boundary loops` из `boundary edges`) корректно определяет замкнутость цикла только когда у каждой вершины границы ровно 2 инцидентных boundary edge; если в вершине сходится больше рёбер (типичный случай — два разных отверстия касаются друг друга ровно в одной точке), однозначно упорядочить цикл нельзя, и кандидат помечается `is_closed=false` (см. §3.5.4-подобный разбор в `CLAUDE.md`), даже если запаивание само по себе прошло успешно. В этом случае (и, по той же логике, при `close_candidates`) как fallback берутся уже **запаянные заплатки** (`sealed_mesh`, связные компоненты новых граней — см. §3.1.2) и пересчитываются те же три критерия напрямую по ним:
- периметр — сумма длин рёбер каёмки заплатки (не требует упорядочивания в цикл);
- площадь — сумма площадей собственных треугольников заплатки (реальная площадь искривлённой поверхности, а не приближение плоским многоугольником);
- расстояние до скелета — от центроида каёмки заплатки.

Оценка кандидатов-заплаток теми же весами/`ambiguity_ratio` может как разрешить `attachment_loop_not_closed` (эти признаки всегда корректно определены, в отличие от упорядочивания цикла), так и иначе разрешить `close_candidates` (реальная площадь заплатки может отличаться от площади плоского многоугольника заметнее, чем разница между кандидатами). Если и по заплаткам результат неоднозначен — объект остаётся `needs_review` с исходной причиной. Метод, которым в итоге определена область крепления, сохраняется в `attachment_method` (`"loop"` или `"patch_fallback"`).

Логику поиска attachment loop вынести в единую функцию, например:

```text
detect_attachment_loop(mesh, branch_skeleton)
```

и использовать эту же функцию в этапах 1 и 3, чтобы область крепления определялась одинаково во всём pipeline.

#### 3.1.2. Запаивание и фиксация attachment cap

После определения `attachment loop` выполняется существующий алгоритм запаивания всех отверстий.

При этом необходимо отдельно сохранить **только информацию о новых гранях, которыми была закрыта исходная область крепления шипика**.

Для мелких побочных отверстий, которые также были запаяны для получения watertight mesh, отдельную маску или списки граней сохранять не требуется.

Для attachment region сохранить минимум:

```text
attachment_loop_vertex_indices
attachment_loop_edges
attachment_loop_centroid_global
attachment_loop_perimeter
attachment_loop_area
attachment_loop_distance_to_branch_skeleton
attachment_cap_face_indices
attachment_cap_area
attachment_ambiguous
attachment_method
candidate_loops
candidate_patches
```

`attachment_method` — `"loop"` (обычный случай, §3.1.1 шаги 1–4) или `"patch_fallback"` (см. выше). `candidate_loops`/`candidate_patches` — сводка (периметр/площадь/расстояние/скор) по всем кандидатам обоих методов, для отладки/визуальной проверки (`spine-preprocessing-visual-check.ipynb`, график "1b"), независимо от того, какой метод в итоге выбрал область крепления.

`attachment_cap_face_indices` — индексы **только тех новых граней в sealed mesh**, которые были созданы при заполнении выбранного `attachment loop`.

Рекомендуемый sidecar-файл:

```text
attachment_region_<исходное_название_мэша>.json
```

Топология `sealed_mesh` и `local_sealed_mesh` одинакова, поэтому `attachment_cap_face_indices` после жёсткого преобразования координат остаются теми же.


#### 3.1.3. QC запаянного mesh

Для полученного запаянного mesh проверить:

- `boundary_edges == 0`;
- connected components;
- degenerate faces;
- manifoldness;
- normals;
- self-intersections;
- finite coordinates;
- положительный finite volume.

Сохранить:

```text
is_watertight
is_manifold
n_boundary_edges_before
n_boundary_edges_after
n_holes_before
n_holes_filled
attachment_cap_area
volume
```

Полученный запаянный mesh должен быть сохранён в папку `<исходное_название_мэша>` (`spine_<spine_id>`) c названием:

```text
sealed_<исходное_название_мэша>.off
```

Итоговый путь:

```text
/preprocessed/<neuron_id>/limb_<limb_id>/branch_<branch_id>/spines/spine_<spine_id>/sealed_<исходное_название_мэша>.off
```

Параметры полученного mesh сохранить в `sealed_spines.parquet`.

### 3.2. Этап 2. Обнаружение ложных шипиков

**Цель:** Определить `spine_<id>.off`, которые фактически являются фрагментом ствола дендрита. Результат:

```text
valid
invalid
```

**Основная идея детекции** – сравнение скелета предполагаемого шипика со скелетом дендрита, анализ **профиля расстояний вдоль скелета**.

**Алгоритм:**
1) Подгружается скелет родительнского бранча шипика `branch_skeleton.npy`.
2) Выполняется скелетонизация запаянного мэша шипика, полученного на предыдущем этапе.
3) На полученном скелете шипика равномерно берется 10 точек (первая - начало скелета, последняя - конец скелета).
4) Для каждой точки считается кратчайшее расстояние до скелета бранча.
5) Выполняется проверка: если максимальное среди заданных расстояний больше заданного порога*, то шипик валидный, иначе - нет.

*Порог задается отдельно для каждого датасета, на текущем этапе для всех датасетов прописать порог равным 300 нанометров.

Данный алгоритм (без проверки) уже реализован и опробан в ноутбуке `notebooks/exploratory/test_skeleton.ipynb`, использовать данную реализацию + добавить проверку (пункт 5) и сохранение таблицы со статусами шипиков `valid / invalid` в формате `parquet` с полями:

```text
dataset
neuron_id
limb_id
branch_id
spine_id
source_path

status

d_min
d_max
d_mean
d_median
```

### 3.3. Этап 3. Перевод в локальную систему координат

**Цель:** убрать произвольный translation/rotation, сохранив реальный физический scale и ориентацию шипика относительно места его прикрепления к дендриту.

Индивидуальный scaling до unit cube запрещён.

Для определения локальной системы координат используется **запаянный mesh** `sealed_<исходное_название_мэша>.off`. За референсную реализацию перевода в локальную систему координат берется функция `orient_spines()` из файла `notebook_widgets.py`. Данная функция должна использовать сохраненную на первом этапе информацию о запаянной области крепления шипика - attachment cap.

Функцию `orient_spines()` и другие уже реализованные функции изменять запрещено. Необходимо создать отдельную реализацию, например:

```text
orient_spines_w_holes()
```

Полученный после преобразования mesh сохранить как:

```text
local_sealed_<исходное_название_мэша>.off
```

Итоговый путь:

```text
/preprocessed/<neuron_id>/limb_<limb_id>/branch_<branch_id>/spines/spine_<spine_id>/local_sealed_<исходное_название_мэша>.off
```

После того как `global_to_local` вычислен по запаянному mesh, **то же самое преобразование без каких-либо дополнительных пересчётов** необходимо применить к исходному mesh.

Важно: для исходного mesh запрещено повторно определять собственный origin или собственные оси. Исходный и sealed mesh одного шипика должны находиться строго в одной локальной системе координат.

Результат сохранить как:

```text
local_<исходное_название_мэша>.off
```

по адресу:

```text
/preprocessed/<neuron_id>/limb_<limb_id>/branch_<branch_id>/spines/spine_<spine_id>/local_<исходное_название_мэша>.off
```

Информация о преобразовании должна быть сохранена в `transform_<исходное_название_мэша>.json`:
- `origin_global` — точка `O`, центр attachment loop;
- `tangent` — `e_t`;
- `radial` — `e_r`;
- `binormal` — `e_b`;
- `global_to_local` — матрица `4x4`;
- `local_to_global` — обратная матрица `4x4`;
- `orientation_fallback`;
- `attachment_ambiguous`;
- `source_mesh_path`;
- `sealed_mesh_path`.

После преобразования в `attachment_region_<исходное_название_мэша>.json` дополнительно сохранить локальные характеристики области крепления:

```text
attachment_loop_centroid_local
attachment_normal_local
```

## 3.4. Этап 4. Объединение branch

**Цель:** Исправить метаинформацию в случае, когда один непрерывный branch ошибочно разбит на несколько branch.

На текущем этапе достаточно **логического merge**. Физически объединять `.off` пока не требуется.

**Правило**
Использовать логику single_child_merge.py (прикрепленный файл):

объединять `parent -> only child`, если:

- оба branch представлены в limb;
- связь однозначна;
- endpoint не ambiguous;
- limb не cyclic;
- у parent ровно один child.

Транзитивно объединять максимальную цепь.

Через реальную bifurcation merge запрещён.

Для датасетов Minnie и H01 уже выполнен данный алгоритм, его результаты:
- datasets/h01/merged_branches/h01_merged_branches.parquet
- datasets/h01/merged_branches/h01_single_child_merge_mapping.parquet
- /datasets/minnie65/merged_branches/merged_branches.csv
- datasets/minnie65/merged_branches/single_child_merge_mapping.parquet

### 3.5. Этап 5. Проверка геометрической корректности `local_sealed` mesh

**Цель:** перед формированием обучающих представлений убедиться, что `local_sealed<исходное_название_мэша>.off` является геометрически корректной замкнутой поверхностью и что применение локального преобразования не повредило mesh.

Проверка выполняется для:

```text
local_sealed_<исходное_название_мэша>.off
```

#### 3.5.1. Базовые проверки

Для каждого mesh вычислить:

```text
is_watertight
is_manifold
n_vertices
n_faces
n_connected_components
n_boundary_edges
n_degenerate_faces
has_self_intersections
n_self_intersecting_pairs
self_intersection_method
has_consistent_winding
has_finite_coordinates
surface_area
volume
euler_characteristic
genus
```

Дополнительно, только как диагностика (не влияет на `geometry_valid`/`quality_status`, которые определяются исключительно по `local_sealed_mesh`), проверить самопересечения и на **исходном незапаянном mesh** — это позволяет отличить дефект, унаследованный из сырых данных, от дефекта, привнесённого запаиванием (см. §3.5.4):

```text
original_has_self_intersections
original_n_self_intersecting_pairs
original_self_intersection_method
```

Для замкнутой ориентируемой поверхности:

```math
\chi=V-E+F,
```

```math
\chi=2-2g,
```

где `g` — род поверхности.

Для обычного корректно запаянного изолированного шипика ожидается:

```math
g=0.
```

`genus != 0` не должен автоматически означать биологическую ошибку, однако такой объект необходимо пометить `needs_review`, поскольку для одиночного spine это чаще указывает на дефект реконструкции или запаивания.

#### 3.5.2. Проверка инвариантности после `global_to_local`

Необходимо сравнить `sealed_mesh` и `local_sealed_mesh`.

После rotation + translation должны совпадать с допустимой численной погрешностью:

```text
n_vertices
n_faces
edge lengths
surface_area
volume
attachment_cap_area
```

Также необходимо проверить обратимость преобразования:

```math
p_{reconstructed}=T_{local\rightarrow global}(T_{global\rightarrow local}(p)).
```

Максимальная ошибка восстановления координат:

```text
transform_roundtrip_error_max
```

должна быть меньше заданного `transform_tolerance`.

#### 3.5.3. Правила статуса

`geometry_valid=true`, если одновременно выполняются как минимум:

- mesh watertight;
- mesh manifold;
- `n_connected_components == 1`;
- отсутствуют non-finite coordinates;
- отсутствуют вырожденные грани выше допустимого порога;
- `volume > 0`;
- round-trip transform проходит tolerance.

Следующие признаки должны переводить объект в `needs_review`:

```text
self_intersections
genus != 0
inconsistent winding
multiple connected components
```

Результаты сохранить в:

```text
quality_<исходное_название_мэша>.json
```

и агрегированно в:

```text
mesh_quality.parquet
```

Только объекты с разрешённым для обучения статусом передаются в этапы 3.6–3.8 (`allow_needs_review=true` по умолчанию — см. §5 — означает, что `valid` и `needs_review` оба разрешены; `invalid` не передаётся никогда).

#### 3.5.4. Самопересечения: интерпретация и влияние на последующие этапы

`self_intersections` — единственный из признаков `needs_review`, который в реальных данных Minnie65 наблюдается чаще всего, причём как минимум частично уже присутствует в исходном (незапаянном) mesh — то есть является дефектом сегментации, а не запаивания (см. `original_has_self_intersections` в §3.5.1). Запаивание мелких побочных отверстий рядом с уже проблемной областью может добавить ещё несколько пересекающихся пар. Автоматическое устранение самопересечений на этапе предобработки **не выполняется** — исправление геометрии рискует исказить реальную биологическую форму именно в этой области; вместо этого объект помечается `needs_review` для точечного разбора.

Практическое влияние на этапы 3.6–3.8 (при небольшом числе пересекающихся пар относительно общего числа граней, как в наблюдаемых случаях):

- **Point cloud (3.6):** семплирование по площади треугольников не требует несамопересекающейся поверхности — каждая точка остаётся корректной точкой на одной из граней; в области пересечения плотность точек может быть немного искажена.
- **SDF (3.7):** знак определяется через generalized winding number, который специально устойчив к небольшим самопересечениям (в отличие от четно-нечетных методов трассировки лучей); `sdf_valid`/sanity-проверки (§3.7.2, §3.7.7) остаются дополнительной защитой.
- **Морфометрики (3.8):** `Volume`/`Area`/`ConvexHull*` вычисляются CGAL по замкнутой ориентированной поверхности как определённая величина независимо от самопересечения; локальная погрешность ограничена размером пересекающегося участка относительно всего объекта.

Иными словами, самопересечения не являются для этих этапов блокирующей ошибкой (в отличие от `is_watertight=false` или `volume<=0`, что уже относится к `invalid`), но и не гарантированно нулевой по эффекту — именно поэтому статус `needs_review`, а не `valid`.

### 3.6. Этап 6. Преобразование mesh в облако точек

**Цель:** получить унифицированное представление поверхности с фиксированным числом точек для моделей, работающих с point cloud.

Источник:

```text
local_sealed_<исходное_название_мэша>.off
```

Использовать исходный список `mesh.vertices` как point cloud запрещено: число и распределение вершин зависят от исходной триангуляции и могут создавать технический признак датасета.

#### 3.6.1. Равномерное семплирование поверхности

Точки необходимо семплировать **по поверхности треугольников пропорционально их площади**.

Для грани `f_i` с площадью `A_i`:

```math
P(f_i)=\frac{A_i}{\sum_j A_j}.
```

После выбора треугольника точка внутри него генерируется по барицентрическим координатам.

Таким образом плотность точек определяется площадью поверхности, а не исходной плотностью вершин mesh.

#### 3.6.2. Размеры облака точек

Для каждого валидного spine сформировать три канонических представления:

```text
2048 points
4096 points
8192 points
```

Для каждого `local_sealed_<исходное_название_мэша>.off` необходимо заранее сформировать 4 независимых варианта семплирования поверхности для каждого количества точек:

```text
pointcloud_2048_1.npz
pointcloud_2048_2.npz
pointcloud_2048_3.npz
pointcloud_2048_4.npz

pointcloud_4096_1.npz
pointcloud_4096_2.npz
pointcloud_4096_3.npz
pointcloud_4096_4.npz

pointcloud_8192_1.npz
pointcloud_8192_2.npz
pointcloud_8192_3.npz
pointcloud_8192_4.npz
```

Каждый вариант должен формироваться одним и тем же алгоритмом area-weighted surface sampling, но с отдельным фиксированным seed.

Зафиксировать четыре значения:

```text
sampling_seed_1
sampling_seed_2
sampling_seed_3
sampling_seed_4
```

Конкретные значения задаются в конфигурации и не должны меняться после формирования версии датасета.

Каждый файл pointcloud_<...>.npz должен содержать минимум:

```text
points              float32 [N, 3]
normals             float32 [N, 3]
face_indices        int32   [N]
is_attachment_cap   bool    [N]
```

`face_indices` — индекс грани исходного `sealed_local` mesh, из которой была получена точка.

`is_attachment_cap` вычисляется по `attachment_cap_face_indices` и позволяет при необходимости исключать точки искусственной области крепления из отдельных потерь или метрик.

Для мелких отверстий, запаянных на этапе 3.1, отдельная маска не требуется.

Таким образом, для одного mesh и одного размера point cloud различается только конкретная случайная выборка точек с поверхности. Геометрия, масштаб, локальная система координат и алгоритм семплирования остаются одинаковыми.

Во время обучения один из четырёх заранее рассчитанных вариантов может случайно выбираться для каждого объекта/эпохи:

```text
spine
→ random choice {1, 2, 3, 4}
→ pointcloud_N_i
```

Это используется как аугментация данных без необходимости выполнять повторное семплирование поверхности во время обучения.


#### 3.6.3. Нормали

Для каждой sampled point сохранить нормаль поверхности.

Предпочтительный вариант:

1. вычислить согласованные вершинные нормали `local_sealed_mesh`;
2. интерполировать три нормали вершин соответствующего треугольника с теми же барицентрическими коэффициентами;
3. нормировать результат:

```math
n_i\leftarrow\frac{n_i}{\|n_i\|}.
```


#### 3.6.4. Scale

Координаты в point cloud должны оставаться в физическом масштабе локальной системы координат.

Запрещено независимо выполнять для каждого объекта:

```text
unit sphere normalization
unit cube normalization
normalization by individual bbox
```

#### 3.6.5. Воспроизводимость

Для канонических файлов `pointcloud_2048/4096/8192` использовать детерминированный seed, зависящий от:

```text
preprocessing_version + spine_id + point_count
```

Это гарантирует одинаковый evaluation input между экспериментами.


### 3.7. Этап 7. Подготовка данных для SDF

SDF-декодер не обучается непосредственно по списку треугольников mesh. Для обучения ему необходимы пары:

```math
(q_i, d_i),
```

где:

- `q_i` — произвольная 3D-точка в окрестности шипика;
- `d_i` — signed distance от этой точки до поверхности `local_sealed_mesh`.

Поэтому из каждого валидного замкнутого mesh заранее формируется набор SDF samples.

#### 3.7.1. Определение SDF

Зафиксировать единую знаковую конвенцию:

```math
d(q)=
\begin{cases}
-\operatorname{dist}(q,\partial S), & q\text{ внутри mesh},\\
0, & q\text{ на поверхности},\\
+\operatorname{dist}(q,\partial S), & q\text{ вне mesh}.
\end{cases}
```

Поверхность соответствует нулевому уровню:

```math
S=\{q:f(q)=0\}.
```

SDF необходимо вычислять именно относительно:

```text
local_sealed_<исходное_название_мэша>.off
```

поскольку корректный знак `inside/outside` требует замкнутой поверхности.

#### 3.7.2. Определение знака inside / outside

Для определения знака рекомендуется использовать устойчивый алгоритм для watertight mesh, например generalized winding number либо эквивалентный robust inside/outside test.

Для каждого объекта необходимо выполнить sanity-check:

- заведомо внешняя точка имеет `d > 0`;
- точка внутри объёма имеет `d < 0`;
- sampled surface points имеют `|d|` близкое к нулю.

При нарушении знаковой конвенции объект не должен попадать в обучение SDF-модели.

#### 3.7.3. Типы query points

Для каждого spine сформировать смесь трёх типов точек:

```math
Q=Q_{surface}\cup Q_{near}\cup Q_{uniform}.
```

##### `Q_surface`

Точки, семплированные непосредственно с поверхности mesh.

Для них:

```math
d(q)\approx0.
```

Они необходимы для точного восстановления нулевого уровня поверхности.

##### `Q_near`

Точки в окрестности поверхности:

```math
q=p+\epsilon,
```

где `p` — точка поверхности, а `epsilon` — небольшой 3D-шум.

Использовать несколько глобально заданных масштабов шума:

```text
sdf_near_sigma_small
sdf_near_sigma_medium
sdf_near_sigma_large
```

в физических единицах. Значения одинаковы для всех spine в рамках версии preprocessing и не зависят от индивидуального размера объекта.

Near-surface samples особенно важны для точного восстановления тонкой шейки, изгибов и локальной кривизны.

##### `Q_uniform`

Точки, равномерно семплированные в 3D-области вокруг шипика.

Область строится как bounding box конкретного `local_sealed_mesh`, расширенный на **фиксированный физический margin**, одинаково заданный для всех объектов.

Индивидуально масштабировать bounding box до unit cube запрещено.

Uniform samples необходимы, чтобы decoder учил не только саму границу, но и корректный знак/расстояние в окружающем пространстве.

#### 3.7.4. Соотношение типов точек

Стартовая конфигурация:

```text
surface       20%
near-surface  60%
uniform       20%
```

Соотношение является параметром config и может быть изменено по результатам validation.

Рекомендуемый стартовый размер сохранённого пула:

```text
sdf_pool_size = 16384 points per spine
```

Если storage позволяет, значение можно увеличить до `32768`.

Во время обучения из сохранённого пула выбирается случайный minibatch SDF queries; декодировать весь пул за один forward pass не требуется.

#### 3.7.5. Что сохранять

Файл:

```text
sdf_samples.npz
```

должен содержать минимум:

```text
query_points      float32 [M, 3]
sdf               float32 [M]
sample_type       uint8   [M]
surface_normals   float32 [M, 3]   # NaN/0 для точек, где нормаль не задана
is_attachment_cap bool    [M]
```

Коды `sample_type` зафиксировать в config/документации, например:

```text
0 = surface
1 = near_surface
2 = uniform
```

Для `surface` и `near_surface` желательно сохранять связь с исходной sampled surface point либо хотя бы признак `is_attachment_cap`.

#### 3.7.6. Не обрезать SDF на этапе preprocessing

В preprocessing сохранять **полное signed distance**.

Если при обучении потребуется Truncated SDF:

```math
\tilde d=\operatorname{clip}(d,-\tau,\tau),
```

обрезание выполнять в `Dataset/DataLoader` модели.

Это позволяет экспериментировать с различными `tau` без повторного вычисления SDF для всего датасета.

#### 3.7.7. QC SDF samples

Для каждого файла проверить:

```text
all finite
both positive and negative distances are present
surface |sdf| <= sdf_surface_tolerance
query points are in local coordinates
sample counts match config
```

Результаты добавить в `quality_<исходное_название_мэша>.json`:

```text
sdf_valid
sdf_min
sdf_max
sdf_abs_mean
n_surface_samples
n_near_samples
n_uniform_samples
```

### 3.8. Этап 8. Морфологические признаки (`morphometrics.json`)

**Цель:** рассчитать морфометрические характеристики шипика для `morphometrics.json`, используя уже реализованные метрики из `src/spine_analysis` (`shape_metric/float_metric.py`, `histogram_metric.py`, `junction_metric.py`).

Как и в остальных production-представлениях, метрики считаются по:

```text
local_sealed_<исходное_название_мэша>.off
```

а не по `sealed_<...>.off` в глобальных координатах.

Набор метрик:

```text
OldChordDistribution
OpenAngle
CVD
AverageDistance
LengthVolumeRatio
LengthAreaRatio
JunctionArea
Length
Area
Volume
ConvexHullVolume
ConvexHullRatio
```

#### 3.8.1. Определение области крепления для метрик

Часть метрик (`OpenAngle`, `CVD`, `AverageDistance`, `Length`, `LengthVolumeRatio`, `LengthAreaRatio`) в `src/spine_analysis` (`JunctionSpineMetric` и наследники, `junction_metric.py`) используют для расчёта только **точку** — центр области крепления (`self._junction_center`), от которой меряются расстояния до всех вершин mesh. Эта точка регистрируется через `register_attachment_center()` и используется классами метрик напрямую, **без** какого-либо пересчёта (`_calculate_junction_center()` при зарегистрированной точке возвращает её как есть, не находит центр заново). Поскольку `orient_spines_w_holes()` (этап 3) строит локальную систему координат с началом ровно в центре attachment loop, для `local_sealed_mesh` достаточно зарегистрировать:

```text
attachment_center_local = (0, 0, 0)
```

то есть для этих метрик используется **та же самая точка**, которая была определена на этапах 1/3 (центр attachment loop), без приближений. Числовая эквивалентность с прежней схемой (`sealed_mesh` + глобальный `origin_global`) проверена на реальных данных: максимальное отклонение — порядка `1e-3` из ~`2.6e8` (Volume) и меньше для остальных метрик — это просто ошибка округления от твёрдого преобразования (поворот + перенос), а не другая точка.

**`Area` — особый случай.** `AreaSpineMetric` в `src/spine_analysis` вычисляет `area(mesh) - junction_area`, где `junction_area` — это НЕ площадь attachment loop/cap из этапа 1, а площадь **отдельно, заново найденного набора граней** (`_get_junction_triangles`): ближайшая к зарегистрированной точке грань плюс её грани-соседи по общей вершине (1 грубое кольцо соседей), т.е. независимая от этапа 1 и обычно куда более грубая оценка области крепления, чем `attachment_cap_face_indices`. На реальных данных эта грубая оценка отличалась от точной площади крышки (`attachment_cap_area`, этап 1) на 40–130% (пример: 60069 против 42303 нм² для одного шипика, 65191 против 28150 нм² — для другого).

Поэтому для `Area` `AreaSpineMetric` **не вызывается вообще** — значение считается напрямую:

```text
Area = mesh.area - attachment_cap_area
```

где `mesh.area` — полная площадь `local_sealed_mesh` (совпадает у trimesh и CGAL с точностью до `1e-9`, отдельный расчёт через CGAL не нужен), а `attachment_cap_area` — то самое значение, определённое на этапе 1 (`attachment_region_<исходное_название_мэша>.json`). Так гарантируется, что во ВСЕХ метриках, для которых нужна область крепления, используется ровно та область, которая была определена при запаивании, а не независимо переопределённая внутри `src/spine_analysis`.

`JunctionArea` также не пересчитывается через `src/spine_analysis`: используется уже сохранённое на этапе 1 значение `attachment_loop_area` (площадь исходного контура дырки, а не крышки) из `attachment_region_<исходное_название_мэша>.json`.

#### 3.8.2. `OldChordDistribution` — сохранение и известное ограничение воспроизводимости

`OldChordDistributionSpineMetric` возвращает не скаляр, а гистограмму фиксированной длины (по умолчанию 100 бинов). Формат хранения:

- в `morphometrics.json` — список из 100 чисел (`list[float]`);
- в агрегированной `morphometrics.parquet` — колонка типа `list<double>` (pandas/pyarrow это поддерживают нативно, отдельная таблица не нужна).

**Важное ограничение:** внутри `OldChordDistributionSpineMetric` (`src/spine_analysis/shape_metric/histogram_metric.py`) используется `rand = Random()` — генератор без фиксированного seed, создаваемый заново при каждом вызове. Значение `OldChordDistribution` **не воспроизводимо** между запусками даже для одного и того же mesh (остальные 11 метрик — детерминированные величины и не подвержены этому). Модифицировать `src/spine_analysis` для фиксации seed не требуется/не предполагается на этом этапе; ограничение фиксируется как известное, значение сохраняется как «лучший снимок на момент прогона».

#### 3.8.3. Область применения

Этап 8 запускается только для шипиков, дошедших до `local_sealed_mesh` и допущенных к обучающим представлениям (тот же критерий, что для этапов 6–7: `false_spine == valid`, `quality_status` разрешён конфигом `allow_needs_review`).

### 3.9. Этап 9. Метаинформация (`metadata.json`)

**Цель:** определить и сохранить биологический контекст шипика независимо от геометрического качества конкретного mesh — метаинформация нужна для стратификации и (в будущем) для условной генерации, поэтому рассчитывается для **всех** обнаруженных шипиков, а не только для валидных.

```text
species
health
cell_type
cell_type_binary
compartment
```

#### 3.9.1. `species`

```text
h01     -> human
minnie  -> mouse
labid   -> mouse
```

#### 3.9.2. `health`

```text
h01     -> healthy
minnie  -> healthy
labid   -> healthy / degeneration (правило разметки конкретного шипика/ветви уточняется отдельно)
```

#### 3.9.3. `cell_type` и `cell_type_binary`

Для Minnie тип клетки хранится на уровне **нейрона** (`datasets/minnie65/cell_types_with_nucleus.csv`, колонки `segment_id`, `cell_type`) и наследуется всеми лимбами/ветвями/шипиками этого нейрона.

`cell_type_binary` — сопоставление конкретных значений `cell_type` с `excitatory`/`inhibitory` по таксономии MICrONS:

```text
excitatory: 23P, 4P, 5P-IT, 5P-NP, 5P-PT, 6P-CT, 6P-IT, 6P-U, WM-P, Unsure E
inhibitory: BC, BPC, MC, NGC, Unsure I
```

Значение `Unsure` (без суффикса) сознательно не относится ни к одной группе — `cell_type_binary = null`.

Для H01 предполагается тот же подход (тип клетки на уровне нейрона + то же сопоставление excitatory/inhibitory), но соответствующий референсный файл для H01 пока отсутствует в `datasets/h01/` — до его появления `cell_type`/`cell_type_binary` для H01 равны `null`. Для LabID сопоставление будет определено отдельно.

#### 3.9.4. `compartment`

Компартмент хранится на уровне **лимбы** (`datasets/minnie65/minnie65_limb_compartments_length_rule.parquet`, колонки `neuron`, `limb_id`, `compartment`) и наследуется всеми ветвями/шипиками этой лимбы. В данных встречаются значения `apical`, `basal`, `uncertain`, `axon_like` — сохраняется значение как есть, без принудительной бинаризации до `апикальный/базальный`.

Для H01 предполагается аналогичный подход; референсный файл для H01 пока отсутствует.

#### 3.9.5. Область применения

В отличие от этапа 8, этап 9 не имеет геометрического критерия допуска — выполняется для каждого обнаруженного `spine_<id>.off`, включая `invalid`/`needs_review`.

## 4. Формат подготовленного датасета

Все результаты одного шипика должны храниться внутри одной папки `spine_<spine_id>` в `/preprocessed/` с зеркальным сохранением иерархии исходного датасета.

Итоговая структура:

```text
/preprocessed/
  <neuron_id>/
    limb_<limb_id>/
      branch_<branch_id>/
        spines/
            spine_<spine_id>/
                local_<исходное_название_мэша>.off
                sealed_<исходное_название_мэша>.off
                local_sealed_<исходное_название_мэша>.off
                attachment_region_<исходное_название_мэша>.json
                pointcloud_2048_1.npz
                pointcloud_2048_2.npz
                pointcloud_2048_3.npz
                pointcloud_2048_4.npz
                pointcloud_4096_1.npz
                pointcloud_4096_2.npz
                pointcloud_4096_3.npz
                pointcloud_4096_4.npz
                pointcloud_8192_1.npz
                pointcloud_8192_2.npz
                pointcloud_8192_3.npz
                pointcloud_8192_4.npz
                sdf_samples.npz
                transform_<исходное_название_мэша>.json
                metadata.json
                morphometrics.json
                quality_<исходное_название_мэша>.json
```

То есть для исходного:

```text
spine_<spine_id>.off
```

запаянный mesh должен находиться по адресу:

```text
/preprocessed/<neuron_id>/limb_<limb_id>/branch_<branch_id>/spines/spine_<spine_id>/sealed_spine_<spine_id>.off
```

а запаянный mesh в локальной системе координат:

```text
/preprocessed/<neuron_id>/limb_<limb_id>/branch_<branch_id>/spines/spine_<spine_id>/local_sealed_spine_<spine_id>.off
```

### 4.1. Назначение файлов

```text
local_<mesh>.off
```
— исходный незапаянный mesh, переведённый в локальную систему координат.

```text
sealed_<mesh>.off
```
— запаянный mesh в исходных глобальных координатах.

```text
local_sealed_<mesh>.off
```
— запаянный mesh в локальной системе координат, **основной канонический mesh для обучения**.

```text
attachment_region_<mesh>.json
```
— информация только об исходной области крепления и соответствующей ей искусственной крышке.

```text
pointcloud_*.npz
```
— канонические облака точек фиксированного размера.

```text
sdf_samples.npz
```
— query points и signed distances для обучения SDF-декодера.

```text
transform_<mesh>.json
```
— обратимые преобразования `global <-> local`.

```text
metadata.json
```
— метаинформация шипика, включая как минимум `species`, `health`, `cell_type`, `cell_type_binary`, `compartment`, исходные идентификаторы и пути.

```text
morphometrics.json
```
— рассчитанные морфологические характеристики.

```text
quality_<mesh>.json
```
— результаты геометрического QC и проверки производных представлений.

### 4.2. Глобальный manifest

Дополнительно в корне `/preprocessed/` рекомендуется хранить:

```text
manifest.parquet
processing_state.sqlite
```

`manifest.parquet` должен содержать по одной строке на spine и как минимум:

```text
dataset
neuron_id
limb_id
original_branch_id
merged_branch_id
spine_id
status
geometry_valid
train_eligible
morphometrics_status
metadata_status
merge_metadata_status
species
health
cell_type
cell_type_binary
compartment
source_path
local_mesh_path
sealed_mesh_path
local_sealed_mesh_path
pointcloud_2048_path
pointcloud_4096_path
pointcloud_8192_path
sdf_samples_path
metadata_path
morphometrics_path
quality_path
preprocessing_version
config_hash
```

Наличие manifest позволяет моделям не обходить файловую систему для поиска данных и гарантирует, что все производные представления относятся к одному и тому же `spine_id`.

## 6. Ошибки

Ошибка одного spine не должна останавливать batch.

Сохранять:

```text
stage
object_id
exception_type
message
traceback
input_path
```

в state DB и/или `errors.parquet`.

После этапа выводить summary:

```text
Processed
Success
False spines
Uncertain
Failed
Needs manual review
```

## 6. Параллелизация

Поддержать `--workers N`.

Параллелизация — между spine.

Необходимо:

- не загружать весь датасет в RAM;
- передавать worker только текущий batch;
- освобождать данные после batch;
- исключить конкурентную запись одного файла;
- сохранять результаты после каждого batch.
